1. 把 SnipApi 从一张大表拆成按能力的小 interface

Worth exploring in-process

Problem

设置、历史、贴图、OCR、翻译、窗口生命周期共用同一个 interface，调用方要学完整张表才能用其中一小块。

Solution

按能力拆 interface 与注册函数，preload 分组成对象；IPC 常量与领域类型分文件，通道名不再和领域类型混住。

Wins
  • interface 缩小；每组的 invariants 只在该组声明
  • 新增设置只扩一组，不动其它组
  • 测试可按组跨 seam
  • 类型与常量分家，减少全量共享的 kernel

证据强度：文件与计数均可直接核对；是否现在拆属于取舍，不是故障。

Problem

主进程与遮罩页之间没有类型化 interface：动作名在发送端与接收端各写一遍，漏改一端就是静默失效。

Solution

把协议常量、payload 类型、发送与接收收进一个遮罩桥 module；overlayUi 只剩 DOM 与样式，screenshot 不再解析字符串，翻译桥并入同一个 seam。

Wins
  • locality：动作定义只在一处
  • 发送/接收不再靠人工对齐
  • 可用假 WebContents 测协议
  • overlayUi 的 implementation 仍可整体替换

证据强度：高。发送端 onTool（overlayUi.ts:895-938）与接收端 switch（screenshot.ts:335-362）是两份并列的动作清单。

Problem

  • 帧源可替换，便于构造测试
  • 普通截图路径不再被长图分支污染
  • ScreenshotService 的 interface 变薄

证据强度：中高。长图字段与循环均在同一个类（screenshot.ts:158-165, :589-637）；拆分后的收益程度属判断。

Problem

历史模块知道贴图输入的形状，并自己算落点；同一套 clamp 规则在两个 module 各有一份。

Solution

pinHistory 只返回图片与尺寸；由 pin module 在贴出时算落点，历史不再 import pin。

Wins
  • seam 单向，依赖图无环
  • 落点规则只在一处
  • 删除重复 clamp
  • 历史可独立测试

证据强度：高（两条 import 与两处落点计算都存在）。注意：import type 在编译后被擦除，运行时没有真实环；这里说的是 seam 方向错误，不是运行时崩溃。

Problem

每加一个设置就要同时改全局 state、handler、广播与托盘/通知文案；OCR 语言的回退判定在 handler 里再包一层，与 ocr 模块内部的调用点并存。

  • 规则不再两份，回退行为一致
  • 领域可测，不必启动整个 app
  • index.ts 回到可一眼读完的装配面

真实风险 vs 风格偏好

真实风险（有代码依据，会导致失效或改动扩散）

  • 遮罩协议双实现：发送端 overlayUi.ts:895-938 与接收端 screenshot.ts:335-362 各自维护动作名，漏改即静默失效。
  • index.ts 单点耦合：9 个 module 的 import、33 处 IPC 注册集中在 boot；OCR 语言的校验/回退入口分散在 index.ts:463-497 与 ocr.ts:543-548，易出现只在其中一处改动的分叉。
  • pinHistory 反向依赖 pin：pinHistory.ts:298-325 自带落点计算并与 pin.ts:113-123 重复；seam 方向错，不修不会立刻崩，但后续改几何会漏一处。
  • 测试面过窄：唯一入口是整机 selftest（index.ts:573-576），纯逻辑没有直接 interface 测试，回归定位成本高。
  • 宽 IPC 暴露高权限动作（低severity）：SnipApi 直接暴露 quit（ipc.ts:191），任何 renderer 页面都能触发退出；contextIsolation 已开且为本地应用，风险等级低，但契约确实过宽。

风格偏好（不构成必须改）

  • App.tsx 650 行：无 bug 证据，只是维护偏好；拆不拆取决于后续 UI 迭代频率。
  • preload 机械转发：这是边界 adapter 的本职；删除测试会失败，因为复杂度会回到每个调用点。不应为了「更深」强行合并。
  • overlayUi 的 CSS / 脚本字符串：注入库页面是既定约束，字符串本身不是缺陷。
  • config 每次读盘：开销可忽略；只有为模块补单测时才值得改成依赖注入。
  • 文件命名与目录结构：本报告不做评价。

Top recommendation

先做 #5：index.ts 收敛为组合根

低行为风险

它是近 8 次提交里出现 5 次的热点，也是所有新设置、新 IPC 的必经之路；只搬装配与校验，不动截图/贴图/OCR 行为， 可以在现有硬约束下先拿到 locality。做完 #5，再做 #2 遮罩桥接—— #2 收益更大但会碰普通截图路径，必须单独排期并先补端到端回归。
